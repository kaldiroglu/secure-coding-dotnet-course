# Chapter 8 — CWE-330/338: Insecure Randomness

**Time budget:** ~45 min · **CWE:** CWE-330 / CWE-338 · **Files:** `src/Vulnerable/Shop.Api/Controllers/AccountRecoveryController.cs` ↔ `src/Fixed/Shop.Api/Controllers/AccountRecoveryController.cs` · test `tests/Shop.Tests/RandomnessTests.cs`

## The weakness in one line

The password-reset token is generated by `System.Random` seeded with a fixed value, so every call produces the exact same byte sequence — an attacker who knows (or guesses) the seed can predict every token ever issued.

## Live demo script

1. Open the Vulnerable `AccountRecoveryController`. Read the `// CWE-330/338` comment aloud — note `new Random(20260607)`. Point out the seed is a literal integer; there is no entropy from the operating system, the clock, or any external source.
2. Hit `GET /account/reset-token` twice → both responses return the identical hex string. The token is supposed to be a secret one-time value; instead it is a deterministic constant.
3. In the test, show `RandomnessTests.Vulnerable_token_is_predictable`: it independently constructs `new Random(20260607)`, calls `NextBytes`, and asserts the hex matches both API responses. The attacker needs only the seed — which is visible in source — to predict the token for any user, past or future.
4. Open the Fixed `AccountRecoveryController` side-by-side: `RandomNumberGenerator.GetBytes(32)` — one static call, no seed, no state. The OS CSPRNG provides 256 bits of entropy.
5. Hit the fixed endpoint twice → tokens differ; the test also verifies the byte length is at least 32 (`>= 32` bytes = 64 hex chars).
6. Run `dotnet test --filter FullyQualifiedName~RandomnessTests` → green.

## Why it's exploitable (the mechanism)

`System.Random` is a linear congruential generator designed for statistical simulations, not security. With a known seed it is entirely deterministic: given the seed, every future (and past) output is computable. Even when the seed is "unknown", time-based seeds (e.g., `new Random()` before .NET 6 used `Environment.TickCount`) have low entropy and can be brute-forced in milliseconds. A predictable reset token means an attacker can request a reset for any account, compute the token, and take over the account without ever receiving the email.

## The fix (and why it's usually less code)

Replace `new Random(seed).NextBytes(buffer)` with `RandomNumberGenerator.GetBytes(count)` (or the equivalent `RandomNumberGenerator.GetHexString`). `RandomNumberGenerator` is backed by the operating-system CSPRNG (`/dev/urandom` on Linux, `BCryptGenRandom` on Windows), which gathers entropy from hardware interrupts, network timing, and other unpredictable sources. The fix is one line shorter: no instantiation, no buffer declaration, no seed management.

## The transferable principle

> **Security tokens come from a CSPRNG.**

## "But what about…" — anticipated questions

- **Q:** What is the difference between `System.Random` and `RandomNumberGenerator`? **A:** `System.Random` is a pseudo-random number generator seeded at construction — the same seed always produces the same sequence. `RandomNumberGenerator` delegates to the OS cryptographic entropy pool; there is no seed you control and no way to reproduce the output. For anything security-sensitive (tokens, nonces, salts, OTPs, session IDs) always use `RandomNumberGenerator`.
- **Q:** Can't I use `Guid.NewGuid()` as a token? **A:** No. `Guid.NewGuid()` generates a version-4 UUID, which has only 122 bits of randomness and its structure is publicly known. More importantly, on older Windows versions (before .NET 6) the implementation could produce guessable GUIDs in certain circumstances, and GUIDs are not guaranteed to be generated from a CSPRNG on all platforms. Use `RandomNumberGenerator` for security tokens; it gives you explicit, guaranteed cryptographic quality.
- **Q:** What about time-seeded `new Random()` — isn't that unpredictable enough? **A:** No. Before .NET 6, `new Random()` used `Environment.TickCount` (milliseconds since boot), which has only ~32 bits of entropy. An attacker can brute-force 2^32 seeds in seconds on modern hardware. .NET 6+ changed the default to a random seed, but the type is still not a CSPRNG and is not suitable for security use. The rule is simple: `System.Random` is for games and simulations; `RandomNumberGenerator` is for security.
